# МЕТОДИЧЕСКИЕ РЕКОМЕНДАЦИИ ПО ВЫПОЛНЕНИЮ КУРСОВОЙ РАБОТЫ

К профессиональному модулю ПМ4 «Разработка браузерных приложений»

Специальность: 06130100 «Программное обеспечение (по видам)»

Квалификация: 4S06130105 «Техник информационных систем»

Статус: проект; параметры утверждения, сроки и тема уточняются руководителем курсовой работы.

## 1. Общие положения

Курсовая работа является самостоятельной проектной работой студента под руководством преподавателя и выполняется с целью закрепления компетенций по Node.js, Express.js, REST API и интеграции с PostgreSQL через Prisma ORM. Основной оцениваемый результат — работающее серверное приложение и документированный репозиторий GitHub.

Рекомендации устанавливают единый порядок выбора темы, проектирования базы данных и HTTP-интерфейса, реализации серверного приложения, оформления пояснительной записки и подготовки к защите. Приоритет отводится работоспособности REST API, корректности модели данных и возможности повторить развёртывание проекта по документации.

## 2. Выбор темы и согласование задания

Студент самостоятельно выбирает тему и согласовывает её с преподавателем. Количество и состав сущностей определяются предметной областью; база данных должна содержать не менее двух взаимосвязанных таблиц, верхнего ограничения нет. До реализации студент представляет описание задач приложения, предварительную ER-диаграмму и перечень HTTP-маршрутов. Изменение согласованной темы допускается по согласованию.

## 3. Требования к результату
- Операционное REST API на Node.js/Express, использующее PostgreSQL и Prisma.
- Полный CRUD по основной сущности, чтение второй сущности, один связанный запрос.
- Валидация, понятные JSON-ошибки и корректные HTTP-статусы.
- Воспроизводимое развёртывание по README в опубликованном GitHub-репозитории.
- Отдельная пояснительная записка, раскрывающая цель, проектирование, реализацию и результаты тестирования.

Название темы курсовой работы должно отражать характер разрабатываемого программного продукта и его предметную область.

Рекомендуемая формулировка:
«Разработка REST API для [наименование или назначение приложения]».

Пример:
#### «Разработка REST API для интернет-магазина мобильных аксессуаров „Mobile Shop“».

При формулировании темы необходимо учитывать следующие требования:
- Название должно отражать разработку серверного REST API.
- Предметная область должна быть конкретной и понятной.
- Допускается использование собственного названия программного продукта.
- Тема должна соответствовать функциональным возможностям разрабатываемого приложения.
- Окончательная формулировка согласовывается с преподавателем.

## 5. Содержание глав

### 5.1. Глава 1 — проектирование
- Постановка задачи: кто и для чего использует API, какие ресурсы доступны.
- Функциональные и нефункциональные требования; обязательные и дополнительные функции.
- Актуальная ER-диаграмма проектируемой базы данных: все основные сущности, первичные и внешние ключи, типы связей. Диаграмма обязательна в пояснительной записке и в README.md. Её можно подготовить в pgAdmin (ERD Tool) или в другом инструменте построения ERD по структуре PostgreSQL/Prisma Schema.
- Таблица REST endpoint с HTTP-методом, URL, назначением, входными и выходными данными.
- Обоснование выбора Node.js, Express, Prisma и PostgreSQL.

### 5.2. Глава 2 — реализация и тестирование
- Организация каталога проекта, схема Route → Controller → Service → Prisma → PostgreSQL.
- Примеры Prisma Schema и настройки доступа к базе (без публикации секретов).
- Пример реализации CRUD основной сущности; получение связанных данных.
- Примеры middleware валидации и централизованного errorHandler.
- Протокол тестирования: успешное создание, чтение, редактирование, удаление; ошибочные поля, отсутствующий ID, некорректные связи.
- Порядок запуска проекта по README и подтверждение воспроизводимости.

## 6. Практическая последовательность работы
1. Согласовать тему; описать 2–3 сценария использования.
1. Спроектировать структуру данных, определить необходимое количество таблиц (не менее двух взаимосвязанных), создать ER-диаграмму и согласовать перечень HTTP-маршрутов.
1. Создать репозиторий и Node.js-проект; настроить .gitignore и .env.example.
1. Подключить PostgreSQL, Prisma Schema, подготовить структуру БД.
1. Реализовать маршруты, контроллеры, сервисы; выполнить CRUD.
1. Добавить проверки входных данных, ошибки 400/404/409/500.
1. Подготовить примеры данных и проверить API с помощью HTTP-клиента.
1. Подготовить README.md: требования, установка, .env.example, настройка и запуск PostgreSQL/Prisma, примеры запросов и ответов, ER-диаграмма; проверить развёртывание по инструкции.
1. Оформить пояснительную записку; подготовить выступление и демонстрацию.

## 8. Проверка качества и тестовые сценарии

| Сценарий | Ожидаемое поведение |
| --- | --- |
| GET /api/resources | 200 и массив JSON |
| GET /api/resources/:id (существует) | 200 и объект |
| GET /api/resources/:id (нет) | 404 и JSON-ошибка |
| POST с корректным JSON | 201 и созданная запись |
| POST с некорректным телом | 400 и сообщение об ошибке |
| PATCH с корректным полем | 200 и обновлённая запись |
| DELETE по существующему ID | Успешный статус согласно контракту |
| Запрос с нарушением FOREIGN KEY | Управляемая ошибка, например 409 |
| Неизвестный маршрут | 404 |
| Перезапуск сервера | Данные сохранены в PostgreSQL |

## 9. README.md и публикация

README.md должен позволять преподавателю установить зависимости, настроить переменные окружения, подготовить PostgreSQL, создать или восстановить структуру БД, запустить сервер и проверить API без дополнительных разъяснений. Обязательно разместить актуальную ER-диаграмму с ключами и связями непосредственно в README.md (например, как изображение из каталога docs/). Та же диаграмма должна присутствовать в пояснительной записке. Скриншоты не заменяют команды и примеры HTTP-запросов. Запрещено публиковать в GitHub пароли, токены, файл .env и конфиденциальные сведения.

## 10. Дополнительные возможности по РУП

По желанию студент добавляет функционал РО 4.4: JWT, хеширование паролей, роли, CORS, защитные middleware, загрузка файлов, клиентский интерфейс. РО 4.5: Jest, Supertest, CI GitHub Actions, Render/VPS, журналирование и проверки после развёртывания. Эти элементы должны быть описаны в README и показаны при защите.

## 11. Порядок защиты курсовой работы

Для защиты рекомендуется доклад продолжительностью 5–7 минут и презентация объёмом до 15 слайдов. Студент характеризует задачу, показывает ER-диаграмму и архитектуру приложения, демонстрирует запросы GET/POST/PATCH/DELETE и обработку ошибок. Затем объясняет роль Prisma, подтверждает размещение исходного кода и документации на GitHub и отвечает на вопросы комиссии.

## 12. Оценивание

Рекомендуется применять единую 100-балльную шкалу технического задания: проектирование — 15, REST CRUD — 25, Prisma и БД — 15, валидация и ошибки — 15, архитектура — 10, GitHub/README — 10, демонстрация/ответы — 10. Итоговые критерии требуют согласования с правилами колледжа.

## 13. Типичные ошибки
- Вместо реальной PostgreSQL используется массив в памяти.
- Нет связанных сущностей или таблицы никак не связаны.
- CRUD существует формально, но часть методов не работает.
- Prisma-запросы размещены непосредственно в маршрутах без разделения слоёв.
- Не проверяются типы и обязательные поля; ошибки приводят к HTTP 500.
- В репозитории отсутствует .env.example или опубликован пароль.
- README.md не содержит инструкции по настройке и запуску PostgreSQL/Prisma, примеров HTTP-запросов или обязательной ER-диаграммы.
- Работа демонстрируется только на ПК автора и не запускается по документации.
