## 1. Общие положения

Курсовая работа является самостоятельной проектной работой студента под руководством преподавателя и выполняется с целью закрепления компетенций по Node.js, Express.js, REST API, интеграции с PostgreSQL через Prisma ORM, аутентификации пользователей и авторизации по ролям. Основной оцениваемый результат — работающее серверное приложение и документированный репозиторий GitHub.

Рекомендации устанавливают единый порядок выбора темы, проектирования базы данных и HTTP-интерфейса, реализации серверного приложения, оформления пояснительной записки и подготовки к защите. Приоритет отводится работоспособности REST API, корректности модели данных, защищённому доступу к ресурсам и возможности повторить развёртывание проекта по документации.

## 2. Выбор темы и согласование задания

Студент самостоятельно выбирает тему и согласовывает её с преподавателем. Рекомендуется использовать **3–5 сущностей**, включая модель пользователей User. Это ориентир, а не жёсткое ограничение: иное количество возможно по согласованию с преподавателем. Минимально необходима связь между двумя сущностями с использованием внешнего ключа. Для любой темы обязательны регистрация, вход с JWT и разграничение доступа для ролей user и admin. До реализации студент представляет описание задач приложения, предварительную ER-диаграмму и перечень HTTP-маршрутов. Изменение согласованной темы допускается по согласованию.

## 3. Требования к результату
- Операционное REST API на Node.js/Express, использующее PostgreSQL и Prisma.
- Полный CRUD по основной сущности, чтение связанной сущности и хотя бы один связанный Prisma-запрос.
- **Обязательная аутентификация**: модель User, регистрация, безопасное хеширование пароля, login и JWT.
- **Обязательная авторизация**: роли user/admin, защищённые маршруты и проверка прав на backend.
- Валидация, понятные JSON-ошибки и корректные HTTP-статусы, включая 401/403.
- Воспроизводимое развёртывание по README в опубликованном GitHub-репозитории.
- Отдельная пояснительная записка, раскрывающая цель, проектирование, реализацию и результаты тестирования.

Название темы курсовой работы должно отражать характер разрабатываемого программного продукта и его предметную область.

Рекомендуемая формулировка:
«Разработка REST API для [наименование или назначение приложения]».

Пример:
## «Разработка REST API для интернет-магазина мобильных аксессуаров „Mobile Shop“».

При формулировании темы необходимо учитывать следующие требования:
- Название должно отражать разработку серверного REST API.
- Предметная область должна быть конкретной и понятной.
- Допускается использование собственного названия программного продукта.
- Тема должна соответствовать функциональным возможностям разрабатываемого приложения.
- Окончательная формулировка согласовывается с преподавателем.

## 8. Проверка качества и тестовые сценарии

| Сценарий | Ожидаемое поведение |
| --- | --- |
| GET /api/resources | 200 и массив JSON |
| GET /api/resources/:id (существует) | 200 и объект |
| GET /api/resources/:id (нет) | 404 и JSON-ошибка |
| POST с корректным JSON | 201 и созданная запись |
| POST с некорректным телом | 400 и сообщение об ошибке |
| PATCH с корректным полем | 200 и обновлённая запись |
| DELETE по существующему ID | Успешный статус согласно контракту |
| Запрос с нарушением FOREIGN KEY | Управляемая ошибка, например 409 |
| Неизвестный маршрут | 404 |
| POST /api/auth/register с корректными данными | 201, создан user с ролью user, без passwordHash в ответе |
| Повторная регистрация email | 409 или иной согласованный статус конфликта, запись не дублируется |
| POST /api/auth/login с верным паролем | 200, user и accessToken без passwordHash |
| POST /api/auth/login с неверным паролем или неизвестным email | 401, одинаковое внешнее сообщение об ошибке |
| Запрос к защищённому маршруту без JWT | 401 |
| Пользователь role=user обращается к admin-маршруту | 403 |
| Администратор обращается к admin-маршруту с действительным JWT | Успешная операция согласно контракту |
| Попытка указать role=admin при публичной регистрации | Сохраняется роль user |
| Перезапуск сервера | Данные сохранены в PostgreSQL |

## 9. README.md и публикация

README.md должен позволять преподавателю установить зависимости, настроить переменные окружения, подготовить PostgreSQL, создать или восстановить структуру БД, запустить сервер и проверить API без дополнительных разъяснений. Обязательно разместить актуальную ER-диаграмму с ключами и связями непосредственно в README.md (например, как изображение из каталога docs/). Та же диаграмма должна присутствовать в пояснительной записке. В README также должны быть примеры регистрации, login, работы с Bearer JWT, матрица ролей и тесты ответов 401/403. В `.env.example` указываются имена `DATABASE_URL` и `JWT_SECRET` без реальных секретов. Скриншоты не заменяют команды и примеры HTTP-запросов. Запрещено публиковать в GitHub пароли, токены, файл .env и конфиденциальные сведения.

### 9.1. Обязательное описание форматов запросов и ответов API

В `README.md` **каждый реализованный endpoint должен быть документирован**, чтобы его можно было проверить через Postman, Thunder Client, curl или аналогичный HTTP-клиент без изучения исходного кода.

Для каждого endpoint указываются:

1. **HTTP-метод и URL** (например, `POST /api/auth/login`).
2. **Назначение** — какую операцию выполняет запрос.
3. **Доступ** — публичный маршрут или требуется JWT; допустимые роли (`user`, `admin`).
4. **Параметры** — `:id`, query-параметры и их назначение (если есть).
5. **Request Headers** — обязательные заголовки, включая `Content-Type: application/json` для JSON-тела и `Authorization: Bearer <accessToken>` для защищённых маршрутов.
6. **Request Body** — формат и пример JSON для `POST`/`PATCH`/`PUT`, обязательные и необязательные поля; для запросов без тела указать, что тело отсутствует.
7. **Response Body** — пример корректного JSON-ответа, а для `204 No Content` указать отсутствие тела.
8. **HTTP-статусы** — успешный статус и возможные ошибки с кратким описанием и примерами JSON-ответов (в том числе `400`, `401`, `403`, `404`, `409`, если эти случаи предусмотрены маршрутом).

Примеры должны соответствовать **фактически реализованным** маршрутам и структуре объектов проекта. Недопустимо копировать примеры, которые не работают с собственным API. В примерах используются вымышленные пользователи, тестовые данные и условное обозначение токена; реальные пароли, токены и секретные ключи публиковать нельзя.

### 9.2. Образец документации endpoint в README.md

Ниже показан **пример оформления**; реальные URL, имена полей и ответы студент уточняет по своему приложению.

**POST `/api/auth/login` — вход пользователя и получение JWT**

- Доступ: публичный.
- Заголовок: `Content-Type: application/json`.
- Обязательные поля тела: `email` (строка), `password` (строка).

**Request Body:**

```json
{
  "email": "user@example.com",
  "password": "ExamplePassword123!"
}
```

**Успешный ответ — `200 OK`:**

```json
{
  "user": {
    "id": 1,
    "name": "Ivan",
    "email": "user@example.com",
    "role": "user"
  },
  "accessToken": "<JWT>"
}
```

**Ошибка — `401 Unauthorized` (неверные учётные данные):**

```json
{
  "error": "Invalid email or password"
}
```

**Пример защищённого маршрута: `POST /api/products`**

- Доступ: только `admin`; требуется действительный JWT.
- Заголовки: `Content-Type: application/json`, `Authorization: Bearer <accessToken>`.

**Request Body:**

```json
{
  "name": "Keyboard",
  "price": 25000,
  "categoryId": 1,
  "inStock": true
}
```

Для этого маршрута нужно отдельно указать фактический успешный ответ (`201 Created`) и ошибки, например: `400` — неверные данные, `401` — отсутствует/недействителен токен, `403` — недостаточно прав. Названия полей (`categoryId`, `inStock`) приведены только как образец: они должны соответствовать реализации студента.

**Для `GET /api/products`** необходимо привести пример JSON-массива ответа, указать отсутствие Request Body и пояснить, требуется ли JWT.

### 9.3. Проверка полноты документации

Преподаватель должен иметь возможность по одному `README.md`:

- выполнить регистрацию и вход, получить тестовый JWT;

Недостаточно указать только таблицу маршрутов без примеров запросов и ответов. Обязательное документирование API входит в критерий **«GitHub и README»** при оценивании курсовой работы.

## 13. Типичные ошибки
- Вместо реальной PostgreSQL используется массив в памяти.
- Нет связанных сущностей или таблицы никак не связаны.
- CRUD существует формально, но часть методов не работает.
- Отсутствуют регистрация, JWT или защищённые маршруты, хотя это обязательные требования.
- Пароли сохраняются открытым текстом или passwordHash попадает в HTTP-ответ.
- Клиент может назначить себе role=admin при регистрации.
- Проверка роли выполняется только на frontend, а backend не проверяет requireAuth/requireRole.
- Для ресурса с владельцем доверяют userId из body вместо проверенного req.user.id.
- Prisma-запросы размещены непосредственно в маршрутах без разделения слоёв.
- Не проверяются типы и обязательные поля; ошибки приводят к HTTP 500.
- В репозитории отсутствует .env.example или опубликован пароль.
- README.md не содержит инструкции по настройке и запуску PostgreSQL/Prisma, примеров HTTP-запросов или обязательной ER-диаграммы.
- Работа демонстрируется только на ПК автора и не запускается по документации.
